# 运行、事件与维护

## 1. 可观测性

每个请求和后台 Run 使用 trace ID/run ID 串联 API、模型调用、ToolCall、SandboxJob、Artifact 和数据库事件。日志结构化并脱敏；指标用于趋势和告警；trace 用于跨组件定位；审计事件记录安全相关决定。

建议核心指标：

- 服务：请求率、错误率、P50/P95/P99 延迟、饱和度。
- Agent：各终态比例、turn/tool 次数、重试、反思、无进展、恢复成功率。
- 模型：provider 错误、格式失败、token、延迟、费用、fallback。
- 工具：调用成功率、拒绝原因、超时、限流、来源质量。
- 沙盒/Artifact：排队、启动、超时/OOM、策略违规、文件数/字节、验证拒绝和下载授权失败。
- 数据：连接池、慢查询、迁移状态、事件/Artifact 增长和保留清理。

指标必须带受控维度，禁止把 user input、URL 全文或高基数字段直接作为 label。

## 2. SLI、SLO 与告警

为关键用户旅程定义 SLI，例如“可创建并在约定时间内获得非内部错误终态的 Run 比例”。SLO 设定目标与窗口，错误预算指导发布速度。告警应可行动，包含影响、阈值、Runbook 链接和初步定位，不为每个日志错误分页。

安全、数据损坏和错误外部行动可不受普通错误预算容忍，直接高优先级响应。

## 3. Runbook

每类关键告警的 Runbook 包含：症状、用户影响、依赖、仪表盘/查询、初步检查、缓解、恢复验证、升级联系人、禁止操作和后续证据。至少覆盖数据库不可用、模型 provider 故障、搜索限流、Run 堆积、Artifact 存储满、sandbox 不可用和费用异常。

Runbook 命令先在非生产演练；破坏性命令需双人确认和备份。密钥不得复制到事件聊天或工单。

## 4. 事件响应

流程：检测 → 分级 → 指派 Incident Commander → 控制影响 → 定位 → 恢复 → 验证 → 沟通 → 复盘。事件期间优先恢复和降低伤害，根因分析可在服务稳定后深入。

时间线记录事实：时间、观察、决定、行动、结果和负责人。用户沟通说明影响、当前状态和下一次更新时间，不猜测根因。涉及数据或安全时立即启动相应通知和取证流程。

复盘无责但有行动，包含影响、根因、促成因素、检测缺口、响应评价、做得好的部分以及按优先级排序的防复发任务。每项任务有 owner、截止时间和验证方式。

## 5. 维护

- 依赖：定期升级，小批量合入，审查 changelog、许可证和漏洞。
- 数据：执行保留和删除策略，监控增长，验证恢复演练。
- 模型：监控版本漂移，升级前离线评测和小流量灰度。
- 测试：治理 flaky、慢测试和低价值重复测试。
- 技术债：记录影响和利息，与功能同一优先级框架评估。
- 文档：每次事故、接口或操作变化后同步更新。

## 6. 退役

退役功能/模型/工具/API 前统计使用，提供替代和迁移窗口，通知用户，冻结新接入。最后撤销凭据和权限、停止任务、处理数据和 Artifact、删除告警与基础设施、保留必要审计记录，并验证不存在调用方和持续费用。
