# 产品愿景与需求管理

## 1. 产品北极星

Astra 的方向是“面向真实工作的 AI 原生通用 Agent 平台”：把用户目标转化为可持续执行、可验证、可恢复的工作，而不是局限于代码生成。研究、文档、表格、浏览器、数据、消息、日历和业务系统等能力应共享同一 Agent Kernel、权限模型、状态机、记忆和验证机制。

产品决策优先回答：目标用户是否能更可靠、更少人工干预地完成真实任务；完成过程是否透明、安全且可控制；新能力是否增强通用平台，而非形成不可维护的领域特例。

## 2. 发现阶段

每项较大投入先形成机会说明：

- 用户是谁，在什么情境下遇到什么问题。
- 当前替代方案、频率、耗时、失败成本和风险。
- 期望结果及可量化基线，例如任务完成率、人工接管率、端到端耗时、单次成本。
- 为什么现在做；若不做会怎样。
- 证据来源：访谈、运行数据、工单、竞品研究或实验，不使用无来源的主观断言。

探索性原型用于验证最大未知数，不默认进入生产。原型产生的代码只有在满足正式质量门禁后才能转为产品实现。

## 3. 需求结构

建议一个需求包含以下字段：

```yaml
id: REQ-xxx
title: 简洁、面向结果的标题
problem: 用户问题及证据
personas: [目标角色]
scenarios: [主路径, 边界路径, 失败路径]
in_scope: [本次包含]
out_of_scope: [明确排除]
functional_requirements: []
non_functional_requirements: []
acceptance_criteria: []
metrics: []
dependencies: []
risks: []
owner: 姓名或角色
status: draft|approved|implemented|validated|released|retired
```

功能要求描述系统行为；非功能要求至少评估安全、隐私、可靠性、性能、成本、可访问性、国际化、兼容性、可观测性和可维护性。使用“必须/应该/可以”表达强度，避免“智能、快速、友好”等不可验证形容词。

## 4. Agent 特有需求

Agent 能力不能只描述理想回答，还必须覆盖：

- `TaskContract`：交付物、约束、禁止动作、成功准则和验证方法。
- 工具范围：允许的 capability、permission、risk、side effect 和执行 backend。
- 人机边界：何时自动执行、何时请求批准、何时澄清、何时拒绝。
- 预算：模型调用、turn、工具、时间、token、外部 API 和存储上限。
- 不确定性：来源冲突、低置信度、部分完成和无进展时的行为。
- 终态：`completed`、`completed_with_warnings`、`waiting_user`、`blocked`、`failed` 的判定。
- 可审计性：需要保留哪些决策摘要、Observation、Evidence、Artifact 和错误信息。
- 评测：确定性测试集、模型质量集、对抗样本和回归阈值。

## 5. 验收标准

验收标准采用 Given/When/Then 或等价的前置条件—操作—结果形式，并包含：

1. 主成功路径。
2. 无效输入和边界值。
3. 未授权、高风险或能力不可用。
4. 外部依赖超时、限流和部分失败。
5. 恢复、重试、幂等和取消。
6. 日志、指标、事件和审计记录。
7. 兼容性与数据迁移。

示例：给定 sandbox capability 未通过启动探测，当模型请求 `chart.render` 时，该工具不得出现在可用 manifest 中；若仍被请求，运行时必须拒绝并记录稳定错误类别，不得静默降级到较弱隔离。

## 6. 优先级与变更控制

优先级由用户价值、风险降低、战略一致性、时效性、成本和依赖共同决定。可使用 RICE/WSJF 辅助，但评分不能替代判断。安全漏洞、数据完整性和不可恢复风险拥有独立升级通道。

批准后的范围变化必须记录：变化内容、原因、对进度/成本/质量/风险的影响、替代方案、批准人。小的澄清可直接更新同一需求；改变用户结果或架构边界时应创建或修订 OpenSpec change。

## 7. 需求完成定义

需求只有在以下条件同时成立时才算完成：验收标准有测试证据；文档和用户可见说明已更新；监控能观察成功与失败；迁移和回滚已验证；残余风险已接受；发布后指标有观察窗口和负责人。
