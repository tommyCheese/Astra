# 项目计划与交付管理

## 1. 从目标到可交付增量

计划以用户结果为单位，而不是按前端、后端、数据库分别排队。每个增量应能独立演示、验证并在必要时关闭。典型拆解顺序：契约和协议 → 最小纵向切片 → 失败与恢复 → 安全加固 → 可观测性 → 体验和规模化。

里程碑需要明确：目标、范围、不包含项、负责人、依赖、退出标准、目标日期、信心等级和发布方式。日期是基于当前信息的预测；发现新事实后应更新预测并解释变化。

## 2. 估算与容量

先识别工作类型：产品发现、设计、实现、数据迁移、测试、评审、发布、运行准备。估算包含正常路径外的错误处理、测试、文档、可观测性和回滚，且为高不确定任务设置探索时间盒。

团队容量不得全部分配给新功能，应预留缺陷、依赖升级、事故响应和技术债。关键路径上的单点知识需要结对或文档化。

## 3. 风险管理

风险表至少包含概率、影响、暴露时间、触发信号、预防措施、应急方案和 owner。Astra 常见高风险包括：

- 模型输出非确定且随 provider/version 漂移。
- 工具产生真实副作用或越权访问。
- 网页/文档中的 prompt injection 污染决策。
- Artifact、SVG、HTML 或沙盒输出携带主动内容。
- 数据库迁移不可逆、长时间锁表或新旧版本不兼容。
- 外部 API 限流、费用异常或服务中断。
- 日志、Memory、证据包泄露敏感数据。
- 后台进程内任务在服务重启时丢失。

高风险必须在实现前指定验证方式和失败时的安全状态。

## 4. 依赖与决策

外部依赖记录版本、许可证、维护状态、替代方案、SLA、数据处理位置和退出成本。关键技术决策用 ADR 记录背景、决策、备选、后果和复审条件。暂时决策必须标明到期日。

接口依赖应优先通过 schema/contract test 并行推进；数据库变更采用 expand → migrate/backfill → switch → contract，避免要求所有服务同一瞬间升级。

## 5. 交付节奏

推荐使用短周期：补充/评审 OpenSpec → 实现小批量任务 → 持续集成 → 环境验证 → 灰度 → 观察 → 扩大。每日同步阻塞和风险，不用会议代替可追踪记录。

状态建议统一为：`proposed → approved → in_progress → implemented → validated → released → observed → closed`。代码写完只是 implemented，不等于 released 或达到业务结果。

## 6. 变更失败成本控制

- 使用 feature flag/capability gate 隔离未完成能力。
- 先部署向后兼容的数据结构，再启用读写路径。
- 大变更拆成可单独回滚的提交和发布单元。
- 对模型、策略和提示词保存版本快照，使 Run 可复现。
- 对外部副作用使用幂等键、批准记录和结果确认。
- 发布前定义停止条件，如错误率、延迟、费用或任务失败率超阈值。

## 7. 项目健康度

同时观察交付、质量、可靠性与价值：周期时间、部署频率、变更失败率、恢复时间、逃逸缺陷、返工率、需求等待时间、任务完成率、人工接管率、单 Run 成本。指标用于发现系统问题，不用于孤立评价个人产出。
