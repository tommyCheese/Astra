# 发布、部署与回滚

## 1. 环境与版本

环境使用独立数据库、密钥、Artifact 存储和外部 API 配额。构建产物不可变，同一 artifact 从测试环境提升到生产，不在部署时重新构建。版本应能关联 commit、OpenSpec changes、迁移、前后端构建、模型/提示词/策略版本和 SBOM。

## 2. 发布准备

Release Owner 建立发布记录，包含：范围、变更列表、风险等级、依赖、配置差异、迁移步骤、验证方案、监控面板、告警阈值、灰度计划、停止条件、回滚步骤、数据恢复限制、值守人与沟通渠道。

发布前验证备份可恢复，而不是只确认备份任务成功。涉及新 capability 时，先完成运行环境探测；不可用的 backend 不得向模型暴露。

## 3. 推荐部署顺序

1. 冻结并标记 release candidate。
2. 备份并记录恢复点。
3. 执行向后兼容的 expand migration。
4. 部署支持新旧 schema 的后端。
5. 部署前端和异步 worker（若有）。
6. 运行 smoke test：health、创建/读取 Run、事件、关键工具和 Artifact 权限。
7. 对内部用户或小流量启用 feature flag。
8. 观察错误率、延迟、任务终态、模型/工具费用和资源。
9. 逐步扩大；稳定后执行 backfill/contract 阶段。
10. 发布说明和状态沟通。

当前后台使用进程内 `asyncio` 启动 Run 时，部署重启可能中断执行；在引入持久队列和 worker 恢复机制前，发布方案必须考虑排空、暂停新 Run 或明确失败恢复。

## 4. 灰度与停止条件

灰度维度可按用户、workspace、capability 或百分比分组。停止条件必须事先量化，例如：5xx、Run `failed/blocked`、错误完成率、P95 延迟、sandbox 错误、Artifact 拒绝率或单 Run 成本相较基线显著恶化。

停止后首先关闭 flag/路由新流量，再判断回滚应用、回滚配置或前向修复。不得因已经投入成本而扩大有问题的发布。

## 5. 回滚

回滚文档要可直接执行：决策人、触发阈值、命令/步骤、预计时间、数据影响、验证和沟通。应用回滚与数据回滚分开设计。若新版本已写入旧版本不认识的数据，应保留兼容读路径或先停止写入、转换数据后再回滚。

安全策略默认 fail closed。若 sandbox、权限服务或 Artifact 验证不可用，关闭相关 capability；不能静默改用弱隔离。

## 6. 发布后验证

技术观察窗口检查：可用性、错误、延迟、资源、队列、数据库、外部依赖、日志脱敏、告警噪声。产品观察窗口检查：任务成功、人工接管、用户反馈、留存/使用、成本和关键失败类别。

发布完成的定义是：灰度扩大完成、观察窗口无阻断异常、指标达到接受范围、遗留任务已登记、版本说明准确。部署命令成功不等于发布完成。
