# 测试与质量保证

## 1. 质量目标

质量不是“测试通过”单一结果，而是功能正确、安全、可靠、可恢复、可理解且成本可控。测试策略按风险投入：权限、真实副作用、数据迁移、Artifact 主动内容和完成判定属于高风险区域。

## 2. 测试分层

| 层级 | 验证对象 | 典型内容 |
| --- | --- | --- |
| 静态 | 源码与 schema | 类型、lint、依赖与密钥扫描 |
| 单元 | 纯函数/组件 | 状态迁移、策略、校验、错误映射 |
| 组件 | 单服务边界 | Repository、ModelClient、Tool、Sandbox、UI 组件 |
| 集成 | 多组件协作 | API+DB、迁移、Artifact store、外部 provider adapter |
| 契约 | 接口兼容 | 请求响应、ToolSpec、事件、数据库兼容 |
| 端到端 | 用户场景 | 创建 Run、执行、恢复、验证、交付 Artifact |
| 非功能 | 系统属性 | 性能、可靠性、安全、可访问性、灾备 |
| 模型评测 | 非确定行为 | 任务成功、事实性、工具选择、成本和安全 |

测试金字塔用于控制反馈速度，不是限制高价值端到端验证。每个生产缺陷应优先补充能最早发现它的最低层回归测试。

## 3. 测试设计

从验收标准建立 Requirement-to-Test 追踪。对每项行为覆盖等价类、边界值、状态迁移、错误注入、并发和恢复。时间、随机数、网络和模型应可注入或使用 deterministic fake。

Astra 必测矩阵包括：无工具、工具成功、超时、限流、格式错误、未授权、重复调用、结果未知；证据充分/不足/冲突；模型 JSON 非法；预算耗尽；恢复同一 Run；迁移前后数据；沙盒不可用/超时/OOM/策略违规；Artifact 路径逃逸、伪 MIME、超限和未验证下载。

## 4. 模型与 Agent 评测

评测集按任务领域、复杂度、风险、语言和失败模式分层，并保存输入、期望判定、允许差异和评分器版本。指标至少包括：强制成功准则通过率、错误完成率（最危险）、阻塞/澄清准确率、工具选择与参数正确率、来源支持率、人工接管率、P50/P95 延迟、token 和费用。

优先使用确定性 validator；LLM-as-judge 仅作为补充，需校准偏差并抽样人工复核。升级模型或提示词时做配对回归，设置不可突破的安全阈值，而非只比较平均分。

## 5. 环境与数据

环境至少区分 local、test/CI、staging、production；配置差异受版本控制，密钥除外。测试数据使用合成或脱敏数据，提供创建和清理脚本。staging 应尽量复现生产权限、迁移和外部依赖策略，但不得复用生产凭据或无控制复制个人数据。

## 6. 缺陷管理

缺陷记录复现步骤、期望/实际、环境版本、影响范围、证据、严重度和临时缓解。建议：

- S0：安全事件、数据大规模损坏或核心服务不可用，立即响应。
- S1：关键路径大面积失败或存在高风险错误执行，阻断发布。
- S2：重要功能受损但有可接受绕过，计划修复。
- S3：低影响体验或维护问题，进入正常排期。

严重度描述影响，优先级描述修复顺序，两者不可混用。

## 7. 发布质量门禁

发布候选需满足：所有必需检查通过；验收测试有记录；无未接受的 S0/S1；S2 残余风险有 owner 和期限；迁移/回滚演练完成；性能和成本未越阈值；安全扫描和威胁场景通过；监控能区分新旧版本；版本说明准确。

测试失败不能通过“重跑直到绿色”处理。先判断确定性缺陷、环境故障或 flaky test；后者必须登记、指定 owner 和修复期限。
