# Astra 软件开发生命周期

## 1. 目的与原则

本规范定义 Astra 从机会识别到退役的统一工作方式，目标是让需求可追踪、设计可解释、实现可验证、发布可回滚、运行可观测、事故可复盘。它适用于产品功能、Agent 能力、模型与提示词、工具、数据结构、基础设施、前端体验和安全策略。

基本原则：

- 用户价值先于功能数量，成功标准必须可观察。
- Astra 是通用 Agent 平台，任何领域能力都通过稳定内核、策略和工具扩展接入。
- 模型提出意图，确定性运行时负责权限、预算、状态和完成门禁。
- 高风险操作默认拒绝或请求批准；不能以易用性为由绕过安全下限。
- 证据、决策、工具调用和产物必须可审计。
- 小批量、可回滚地交付，以生产反馈驱动下一轮。

## 2. 生命周期与阶段门禁

| 阶段 | 核心问题 | 必要产物 | 退出门禁 | 主责 |
| --- | --- | --- | --- | --- |
| 发现 | 问题真实且值得解决吗 | 机会说明、用户场景、基线数据 | 目标用户、问题和预期结果明确 | Product |
| 需求 | 做什么、不做什么 | PRD、验收标准、追踪矩阵 | 可测试、无关键歧义、风险已分级 | Product + Tech Lead |
| 计划 | 何时、由谁、依赖什么 | 里程碑、估算、风险表、发布策略 | 资源和依赖可行，范围可控 | Project Owner |
| 设计 | 怎样安全可靠地实现 | OpenSpec、架构/数据/API/安全设计 | 关键决策评审通过，可回滚 | Tech Lead |
| 开发 | 实现是否符合设计 | 代码、迁移、测试、文档 | CI 通过、审查完成、无阻断缺陷 | Engineer |
| 验证 | 是否满足功能和质量目标 | 测试报告、验收记录、风险接受 | 验收通过，残余风险有负责人 | QA + Product |
| 发布 | 能否安全进入目标环境 | 版本说明、部署/回滚方案 | 备份、监控、回滚与值守就绪 | Release Owner |
| 运营 | 是否持续稳定地产生价值 | SLI/SLO、告警、Runbook、事件记录 | 持续阶段，以指标触发改进 | Operations |
| 演进/退役 | 应继续、替换还是停止 | 复盘、迁移和退役计划 | 数据处置、依赖下线、用户通知完成 | Product + Tech Lead |

紧急修复可以压缩评审时间，但不能省略可追踪需求、最小验证、回滚方案和事后复盘。

## 3. 角色与责任

- Product Owner：价值、范围、优先级、业务验收与外部承诺。
- Tech Lead：架构一致性、技术风险、非功能需求和最终技术门禁。
- Engineer：设计细化、实现、自测、迁移、可观测性和文档同步。
- QA/Verifier：测试策略、独立验证、缺陷分级和质量报告。
- Security/Privacy Owner：威胁建模、数据分类、权限、供应链与风险接受。
- Release Owner：版本冻结、部署协调、回滚决策和发布沟通。
- Incident Commander：生产事件中的单一指挥、沟通节奏和恢复决策。

小团队可由一人兼任多个角色，但每个门禁必须明确“谁批准”，不能以团队规模为由省略责任归属。

## 4. 追踪模型

建议使用稳定标识串联全部证据：

```text
Opportunity → Requirement → OpenSpec Change → Design Decision
→ Code/DB Migration → Test Case → Release → Metric/Incident
```

每个需求至少关联：成功指标、验收标准、实现变更、测试证据、发布版本。每个生产事故至少反向关联：受影响版本、根因变更、防复发任务。

## 5. Astra 当前工程基线

截至本文建立时，仓库可确认的基线包括：FastAPI + SQLAlchemy/Alembic 后端、React + TypeScript + Vite 前端、pytest 和 Vitest 测试、OpenSpec 变更目录，以及 `Task/Run/Step/ToolCall/Artifact/RunEvent/AgentTurn/Memory/SandboxJob` 等运行记录。开发中能力可能尚未完成其 OpenSpec 任务，必须以对应 `tasks.md` 和测试结果为准，而不是仅凭代码文件存在判断已交付。

## 6. 文档维护

每季度或重大版本后审查本规范。若流程与实际长期不一致，应修订流程或修复执行偏差，不能保留“名义流程”。所有例外需记录原因、批准者、截止日期和补偿措施。
