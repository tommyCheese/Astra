# Astra Agent Platform v0.1

## 1. 北极星

Astra 是一个 AI 原生的通用 Agent 平台，目标是超越现有代码 Agent 和通用聊天助手，把大模型智能转化为可靠的任务执行能力。

产品体验不应该只是“一个能回答问题的聊天框”，也不应该只局限于“一个能改文件的代码助手”。Astra 应该更像一个自主任务伙伴：具备记忆、工具、验证能力，并且能持续理解用户的工作空间、知识环境和外部系统。

核心承诺：

> 给 Astra 一个目标。它会理解背景，形成计划，通过受控工具执行任务，验证结果，并留下可审计的过程记录，说明做了什么以及为什么这样做。

## 2. 什么叫超越 Codex 与通用助手

Astra 竞争的重点不只是模型质量，而是通用任务可靠性。写代码只是其中一个重要场景，真正的目标是让 Agent 能跨越软件工程、知识工作、研究分析、办公自动化、数据处理和业务系统操作。

关键维度：

1. 环境智能
   - 维护结构化的工作空间地图。
   - 理解文件、应用、网页、知识库、代码仓库、数据源和外部服务。
   - 从历史任务、用户偏好、业务规则和领域知识中学习。

2. 持久化执行
   - 把每个任务都视为一次可恢复的运行，包含步骤、状态、证据和产物。
   - 能承受中断。
   - 能从失败的工具调用或过期上下文中恢复，而不是每次从头开始。

3. 验证优先工作流
   - 在执行之前先规划成功标准和验证方式。
   - 根据场景运行测试、构建、数据校验、网页检查、文档比对、业务规则检查、日志检查或人工确认。
   - 报告证据，而不只是报告信心。

4. 工具原生任务能力
   - 使用结构化工具完成文件操作、Shell 命令、Git、浏览器控制、文档、表格、邮件、日历、数据库、云 API、业务系统和内部系统调用。
   - 每次工具调用都要类型化、权限化、日志化、可回放、可限定范围。

5. 多 Agent 协作
   - 支持研究、规划、执行、审查、数据分析、文档、代码、测试、运营和发布等专业 Agent。
   - 通过共享任务状态协调它们，而不是只靠角色扮演提示词。

6. 人类可控
   - 区分低风险、中风险和高风险操作。
   - 在真正有意义的边界请求用户批准。
   - 提供清晰的回滚路径和审计路径。

## 3. 产品定位

初始品类：

> 面向真实工作的 AI 通用 Agent。

初始用户：

- 希望拥有高能力个人助理和执行伙伴的知识工作者。
- 需要自动化研究、文档、数据、代码和业务流程的小型团队。
- 在快速变化环境中构建产品、运营业务或管理知识的 AI 原生团队。

初始切入点：

> 具备工作空间理解能力的、可验证的任务执行。

不要从“什么都能聊”的泛聊天助手开始。要从一个能端到端完成真实任务的通用 Agent 开始，先建立可靠的任务循环，再逐步扩展到更多领域。

## 4. MVP 范围

### 必须具备

1. 工作空间理解
   - 索引文件。
   - 识别项目、文档、数据、代码、网页、应用状态和重要目录。
   - 生成并更新工作空间地图。

2. 任务运行
   - 为每个用户目标创建持久化任务运行。
   - 跟踪状态、计划、步骤、工具调用、产物、验证和最终结果。

3. 规划与执行循环
   - 收集上下文。
   - 生成计划。
   - 执行工具操作、内容修改和外部系统调用。
   - 对失败进行反思。
   - 验证结果。
   - 基于证据总结。

4. 工具运行时
   - 读取和搜索文件。
   - 应用补丁。
   - 运行 Shell 命令。
   - 检查 Git diff。
   - 运行测试和构建。
   - 操作浏览器。
   - 处理文档、表格和数据。
   - 管理任务、日程、消息和业务记录。
   - 调用外部 API。
   - 对前端、网页和业务流程提供可选的浏览器验证。

5. 安全模型
   - 为读取、写入、命令、网络、Git、破坏性操作和外部集成建立权限分类。
   - 对高风险操作引入人工批准。

6. 记忆基础
   - 会话记忆。
   - 工作空间记忆。
   - 持久化任务历史。
   - 用户偏好、项目规则和业务规则。

### 应该具备

1. 研究分析模式。
2. 文档和表格处理模式。
3. 代码和 PR 审查模式。
4. 浏览器任务模式。
5. 多 Agent 审查流程。

### v0.1 暂不包含

1. 完全自主的生产部署。
2. 不受限制的云资源控制。
3. 没有用户意图的长期后台自我派活。
4. 无边界闲聊型消费助手功能。
5. 复杂的组织级知识图谱。

## 6. 核心模块

### 6.1 Agent 编排器

职责：

- 拥有任务生命周期。
- 持久化运行状态。
- 决定使用哪种 Agent 模式。
- 在规划器、执行器、验证器和审查器之间路由。
- 在工具调用前执行策略检查。
- 向用户流式展示有价值的进度。

### 6.2 Agent 内核

内核负责把模型输出转化为受控的任务行为。

组件：

- 规划器：把目标拆解为步骤和验证标准。
- 执行器：通过类型化工具调用执行步骤。
- 反思器：解释失败并修订计划。
- 验证器：通过测试、构建、diff、浏览器检查、数据校验、文档比对或其他证据判断是否完成。
- 记忆管理器：读取和写入相关用户、项目、业务和领域知识。
- 工具路由器：根据意图、风险和环境选择工具。

### 6.3 工具运行时

工具应该被设计成产品基础设施，而不是临时便利封装。

每个工具都应该暴露：

- 名称和版本。
- JSON Schema 输入。
- 结构化输出。
- 权限要求。
- 超时时间。
- 重试策略。
- 副作用分类。
- 审计元数据。

初始工具：

- `workspace.search`
- `workspace.read_file`
- `workspace.apply_patch`
- `shell.run`
- `git.status`
- `git.diff`
- `git.commit`
- `test.run`
- `browser.open`
- `browser.screenshot`
- `browser.inspect`
- `document.read`
- `document.write`
- `spreadsheet.read`
- `spreadsheet.write`
- `data.query`
- `message.send`
- `calendar.create_event`
- `task.create`
- `api.call`

### 6.4 记忆系统

记忆分层：

1. 运行记忆
   - 当前任务目标。
   - 计划。
   - 步骤输出。
   - 工具结果。
   - 失败和重试。

2. 工作空间记忆
   - 项目结构。
   - 文档结构。
   - 数据结构。
   - 构建命令。
   - 测试命令。
   - 框架。
   - 约定。
   - 重要文件。

3. 用户和团队记忆
   - 偏好。
   - 代码风格。
   - 审查风格。
   - 写作风格。
   - 工作流偏好。
   - 风险容忍度。

4. 知识记忆
   - 架构决策。
   - 业务规则。
   - 历史事故。
   - 反复出现的缺陷。
   - 领域术语。

实现方式：

- 将权威记忆保存为结构化记录。
- 使用 Embedding 做召回，而不是把向量库当作事实源。
- 为每条持久记忆附加来源。
- 允许用户检查、置顶、编辑或删除记忆。

## 8. 运行状态机

```text
created
  -> classifying
  -> gathering_context
  -> planning
  -> awaiting_approval
  -> executing
  -> verifying
  -> reviewing
  -> completed

失败路径：
  executing -> recovering -> executing
  verifying -> replanning -> executing
  any_state -> blocked
  any_state -> cancelled
```

状态原则：

- 一次运行必须始终知道下一步要做什么。
- 每次状态转换都应该被持久化。
- 运行应该能在进程重启后恢复。
- 失败应该产生结构化原因，而不只是日志。

## 9. 执行循环

默认循环：

```text
1. 理解目标。
2. 分类风险。
3. 收集工作区上下文。
4. 构建包含验证标准的计划。
5. 必要时请求批准。
6. 一步一步执行。
7. 记录工具调用和产物。
8. 在失败或意外结果后进行反思。
9. 验证最终状态。
10. 基于证据和下一步建议报告结果。
```

重要行为：

- Agent 不应该在没有验证、也没有说明无法验证原因的情况下宣称完成。
- Agent 应该优先选择小而可逆的修改。
- Agent 应该识别用户已有修改和外部状态变化，避免覆盖或破坏它们。
- Agent 应该在执行高风险操作前解释原因。

## 10. 模型策略

Astra 从第一天起就应该支持模型路由。

模型类别：

- 推理模型：规划、研究、分析、架构、调试、复杂代码修改和复杂业务流程。
- 快速模型：简单转换、分类和总结。
- Embedding 模型：检索。
- Reranker：上下文排序。
- 视觉模型：截图、UI 检查、图表和文档。

路由输入：

- 任务类型。
- 风险。
- 上下文大小。
- 延迟目标。
- 成本预算。
- 隐私策略。
- 所需模态。

原则：

> 模型是可替换的基础设施。Agent 系统才是产品。

## 11. 权限模型

权限等级：

1. 读取
   - 搜索和读取工作空间文件。
   - 检查 Git 状态。
   - 读取已授权知识库和应用状态。

2. 写入
   - 修改已批准工作空间根目录内的文件。
   - 创建产物。
   - 更新已授权文档、表格和任务记录。

3. 执行
   - 在沙箱中运行命令。
   - 启动开发服务器。

4. 网络
   - 拉取依赖。
   - 调用外部 API。

5. Git
   - 暂存、提交、创建分支、推送、创建 PR。

6. 外部系统操作
   - 发送邮件。
   - 创建日历事件。
   - 修改 Issue、CRM、数据库或业务系统记录。

7. 破坏性操作
   - 删除文件。
   - 重置状态。
   - 运行会修改外部数据的迁移。
   - 执行不可轻易回滚的业务动作。

策略：

- 读取和低风险写入可以自动执行。
- 命令执行需要根据环境进行范围化审批。
- 网络访问应该显式授权。
- 对外发送、业务系统修改和付费操作必须明确授权。
- 破坏性操作必须由用户明确批准。
- 外部生产环境操作不属于 v0.1 范围。

## 12. 可观测性

平台应该让 Agent 行为可检查。

跟踪内容：

- Prompt 和上下文组装元数据。
- 模型选择。
- 工具调用。
- 步骤状态。
- 错误原因。
- Token 用量。
- 成本。
- 延迟。
- 验证证据。
- 用户批准记录。

用户可见视图：

- 实时运行时间线。
- 计划和步骤进度。
- Diff 查看器。
- 工具调用详情。
- 验证报告。
- 记忆变更。

## 13. MVP 技术栈

推荐初始技术栈：

- 前端：React、TypeScript、Vite。
- 后端：TypeScript + Node.js，或 Python + FastAPI。
- 持久化状态：PostgreSQL。
- 队列：Redis + BullMQ；如果早期优先考虑持久化工作流，可以使用 Temporal。
- 向量检索：v0.1 使用 pgvector。
- 沙箱：先使用本地进程沙箱，之后再引入容器隔离。
- 工具协议：JSON Schema 类型化工具。
- 实时通信：WebSocket 或 Server-Sent Events。
- 认证：初期 local-first，团队版再引入 OAuth/SAML。

默认选择：

> v0.1 优先使用端到端 TypeScript，除非有很强的理由拆分技术栈。这样可以让工具 Schema、UI 类型和后端契约保持接近。

## 14. 第一阶段构建里程碑

### 里程碑 1：工作空间智能

- 创建工作空间。
- 扫描文件、文档、代码、数据和配置。
- 构建工作空间地图。
- 检测可用工具、关键资源和验证方式。
- 展示工作空间摘要。

### 里程碑 2：任务运行引擎

- 创建 Task 和 Run 记录。
- 执行状态机。
- 流式展示进度。
- 持久化步骤和工具调用。

### 里程碑 3：通用工具 Agent

- 搜索文件。
- 读取上下文。
- 生成文件、文档、表格或代码修改。
- 应用变更。
- 展示 diff、变更摘要或产物预览。

### 里程碑 4：验证循环

- 运行测试、构建、数据校验、文档检查或浏览器验证。
- 解释失败。
- 使用修订计划重试。
- 生成证据报告。

### 里程碑 5：记忆

- 存储工作空间约定。
- 存储运行总结。
- 在未来任务中召回相关记忆。
- 允许检查和删除记忆。

### 里程碑 6：审查 Agent

- 审查 diff、文档、数据结果和任务产物。
- 识别缺陷、遗漏、风险和缺失验证。
- 建议修复方案。
- 可选地直接修补问题。

## 15. 开放设计问题

1. v0.1 应该是 local-first、cloud-first，还是混合模式？
2. 执行系统应该从自定义状态机开始，还是一开始就使用 Temporal？
3. 多 Agent 行为应该进入 v0.1，还是等单 Agent 循环足够优秀后再引入？
4. 默认应该开放多少自主性？
5. 哪些任务类型应该成为第一优先级：研究、文档、数据、浏览器操作、代码，还是业务流程？
6. 第一个 UI 应该是桌面应用、Web、CLI，还是 IDE 扩展？
7. 主要成功指标是什么：任务完成率、已验证修改、节省时间、审查质量，还是用户信任？

## 16. 推荐的立即下一步

构建一个很薄的纵向切片：

> 用户输入一个真实任务。Astra 扫描工作空间，创建运行，规划步骤，调用工具完成操作，运行验证，并用产物、变更记录和证据报告结果。

这会证明最核心的循环：

```text
目标 -> 上下文 -> 计划 -> 执行 -> 验证 -> 报告
```

一旦这个循环真实可用，所有高级能力都有坚实的位置可以接入。

## 17. 界面交互设计记忆

以下约定用于保持 Astra 前台在持续演进中的连贯性：

- 临时浮层必须依附于触发它的控件，并避免遮挡主要输入和核心结果。
- 菜单、选择器和非模态浮窗在点击其外部区域时必须收起，同时支持 `Escape` 关闭。
- 同一区域的临时浮层互斥展示；打开新浮层时关闭已有浮层。
- 模态窗口使用明确的关闭按钮和遮罩，点击遮罩可以关闭，但窗口内部操作不能误触关闭。
- 输入区保持两层结构：文本编辑位于上层，附件与模式控制位于底部工具栏，主要提交动作固定在右侧。
- 开关、模型、模式和用量状态必须使用稳定尺寸，动态内容不能导致输入区或浮层重新排版。
- 前端推算的数据必须明确标注为估算；精确 Token、成本和调用统计以后端模型网关数据为准。
- 运行时设置必须把安全边界与性能选项分开表达；沙盒、网络和外部影响属于策略约束，并发、超时和重试属于执行预算。
- Runtime Policy 的界面配置最终应由后端校验和执行，前端不能成为权限边界。
- 设置页按单一职责划分：模型与推理管理认知策略，工具管理能力开关和调用策略，运行时管理环境与任务生命周期，验证与安全管理最终答案的证据标准。
- 模型、推理、规划和反思属于对话级运行配置，应集中在聊天输入区的模型菜单中；工作区设置不重复提供同一入口。
- 有依赖关系的配置采用级联展示：父能力关闭时隐藏或禁用其子配置，并保留用户上一次选择以便重新开启后恢复。
- 国际化当前只支持简体中文与英文；产品界面文案使用统一词典切换，用户输入、模型回答、网页证据和后端业务内容保持原文。
- 语言属于设备级界面偏好，切换后立即生效并在本地持久化；组件不得自行判断语言或维护独立翻译表。
- 主题支持跟随系统、浅色和暗色三种模式；跟随系统时监听系统配色变化，显式选择则作为设备级偏好持久化。
