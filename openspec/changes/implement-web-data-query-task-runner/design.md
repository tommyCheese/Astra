## Context

Astra 当前只有产品与架构文档定义，还没有实现。第一条实现切片必须证明核心 Agent 循环，同时避免把平台过早做重。已选定的切片是：由 Python 服务支撑的 Web App，使用真实模型调用和网络读取工具来运行通用 Web 数据查询任务。

本设计优先保证运行时间线可持久化、可检查，而不是追求宽泛自主性。第一类任务会被刻意约束：Agent 可以规划、搜索、抓取、综合、验证和报告，但不能修改本地文件、发送消息、操作生产系统或运行任意浏览器工作流。

## Goals / Non-Goals

**Goals:**
- 提供一个 Web App，让用户提交通用数据查询目标，并观察实时进度。
- 实现 Python 后端，持久化 Task、Run、Step、ToolCall、Artifact 和最终结果。
- 通过可配置模型客户端和用户提供的 API Key 使用真实模型提供方。
- 实现初始 `web_search` 和 `web_fetch` 工具，并将其作为受审计的网络读取工具调用。
- 生成包含来源、限制说明和验证备注的最终答案。
- 让第一版运行循环足够简单，便于快速实现和测试。

**Non-Goals:**
- 多 Agent 编排。
- 长期记忆或 embedding。
- 团队认证、OAuth 或基于角色的访问控制。
- Temporal、Celery 或生产级分布式工作流执行。
- 本地文件修改工具。
- 不受限制的浏览或外部系统变更。
- 生产部署自动化。

## Decisions

### 后端使用 Python 和 FastAPI

后端将使用 Python 和 FastAPI，因为第一条切片偏重编排，与模型/工具客户端的集成很自然，也能受益于 Python 成熟的异步 HTTP 和数据处理生态。

考虑过的替代方案：
- TypeScript 后端：符合原始 v0.1 推荐，但当前已确认实现方向是 Python。
- Django：成熟，但对第一版 Agent 运行时和流式 API 来说偏重。

### 使用 PostgreSQL 作为持久化运行存储

第一版实现将使用 SQLAlchemy 和 Alembic 将任务执行状态持久化到 PostgreSQL。表结构应直接映射 v0.1 数据模型：Task、Run、Step、ToolCall、Artifact，以及结构化最终结果。

考虑过的替代方案：
- SQLite：本地开发更简单，但 PostgreSQL 能保持设计与未来 pgvector 和并发运行需求一致。
- 内存状态：原型更快，但无法满足运行可检查、可恢复这一核心要求。

### 从进程内异步 runner 开始

Run 将通过后端管理的异步 runner 或后台任务执行。每次状态转换和工具调用都要先持久化，再向客户端流式推送进度。

考虑过的替代方案：
- Celery/RQ/Dramatiq：后续对并发和重试有用，但在运行模型被证明前会增加运维重量。
- Temporal：对持久化工作流很强，但对第一条纵向切片过重。

### 使用 server-sent events 推送实时 timeline

前端将通过 SSE 订阅 run 事件流。SSE 适合后端到 UI 的单向进度流，对初始时间线来说比 WebSocket 更简单。

考虑过的替代方案：
- WebSocket：更适合双向协作，但第一版进度更新不需要。
- 轮询：更简单，但会让时间线不够实时，也会增加 API 请求噪音。

### 将模型输出视为结构化契约

模型客户端将支持用于规划和最终综合的结构化输出。runner 在执行工具调用前必须验证模型生成的计划。

初始结构化输出：
- Plan：步骤、所需工具、成功标准和风险等级。
- Tool decision：选定工具、输入和原因。
- Final answer：摘要、发现、来源、限制说明和验证备注。

考虑过的替代方案：
- 自由文本提示词：启动快，但更难验证、审计和失败恢复。
- 完全自主递归 Agent 循环：能力强，但对第一类任务来说不可预测性过高。

### 拆分 Web 搜索与 Web 抓取

Web 数据查询能力将包含两个网络读取工具：
- `web_search`：将查询转换为带标题/摘要的候选来源 URL。
- `web_fetch`：抓取指定 URL，并返回规范化内容和元数据。

这种拆分能让审计路径更清楚：搜索负责发现来源，抓取负责从选定来源取得证据。

考虑过的替代方案：
- 只做 `web_fetch`：会迫使用户提供 URL，削弱“通用数据查询”体验。
- 浏览器自动化：后续有价值，但对简单来源收集来说过重。

### 第一版权限模型保持明确但收窄

网络读取工具调用是范围内唯一的非本地副作用。每次工具调用都必须记录权限和副作用分类。第一版可以通过配置允许网络读取，但审计记录从第一天就必须存在。

考虑过的替代方案：
- 完整策略引擎：后续合适，但对单一低风险工具类别来说过早。
- 不记录权限元数据：现在更快，但会破坏 Astra 的可审计承诺。

## Risks / Trade-offs

- 模型输出格式错误或不适合执行 -> 验证结构化输出，并让 run 以清晰的 blocked/failed 原因失败，而不是猜测。
- 搜索或抓取提供方返回低质量数据 -> 保留来源元数据，要求限制说明，并展示验证警告。
- 网络抓取可能很慢或失败 -> 设置超时，在 ToolCall 记录中捕获错误；当剩余来源足够时，允许 run 带警告完成。
- SSE 客户端可能断开连接 -> 将 run 状态保存在数据库中，让前端能重连并重新加载当前时间线状态。
- 进程内执行限制扩展性 -> 第一条切片接受这个限制；数据模型应允许未来替换为队列/worker。
- 用户提供的 API Key 具有配置敏感性 -> 从环境配置加载 Key，绝不在 API 响应、日志或工具输出中暴露。

## Migration Plan

1. 搭建后端和前端应用脚手架。
2. 为运行模型增加数据库 schema 和 migration。
3. 增加模型客户端配置和结构化输出接口。
4. 实现进程内 run 状态机和持久化。
5. 实现 `web_search` 和 `web_fetch` 工具适配器。
6. 增加创建 run、读取 run 详情和流式推送 timeline 事件的 API endpoint。
7. 构建 Web App 任务控制台和结果视图。
8. 增加状态转换、工具调用持久化和结果综合契约测试。

由于当前还没有既有产品表面或生产数据，初始构建阶段的回滚很直接。如果后续引入 migration 脚本，回滚应只在本地开发环境中删除新建的 Astra 表。
