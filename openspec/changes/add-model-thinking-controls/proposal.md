## Why

Astra 已能在后端为部分模型映射推理参数，但聊天框只暴露统一的 Agent 推理强度，用户无法知道当前模型是否支持思考、能否关闭思考或有哪些深度档位。需要把模型级思考能力带到模型选择界面，并让每次运行使用经过能力校验的显式配置。

## What Changes

- 建立统一的模型思考能力契约，按 Provider 和模型声明思考开关、可选深度、默认值、是否强制开启及不支持原因。
- 在聊天框的模型选择菜单中为当前模型增加“思考”开关和“思考深度”控制，只展示或启用该模型真实支持的选项。
- 将用户选择按模型记忆，并随创建、继续或批准后的模型请求提交；模型切换时恢复该模型上次有效选择或模型能力默认值。
- 在后端校验并规范化模型级思考选择，再映射为各 Provider 所需的 effort、thinking budget 或 enable-thinking 参数；未知或过期选项安全降级并返回实际生效配置。
- 将模型级思考控制与 Agent 的任务执行策略区分开：前者控制单次大模型推理，后者继续控制计划、工具、反思与验证资源。
- 将模型级思考与界面“思考过程”明确区分：模型设置不得控制过程面板、运行阶段或公开推理摘要是否展示，且界面不得把供应商隐藏思维链当作过程内容。
- 分别评估并提示思考深度对快速模式与可信模式的影响，但回答模式不得决定、限制或自动修改模型思考开关与深度；选择权保持在用户。
- 保持旧客户端兼容：未提交显式模型思考配置时，沿用当前推理策略映射行为。
- 增加能力识别、请求校验、模式组合、过程展示独立性、运行快照、前端交互、可访问性和 Provider 参数映射测试。

## Capabilities

### New Capabilities

- `model-thinking-controls`: 定义模型思考能力发现、模型级开关与深度选择、按模型记忆、请求规范化、兼容降级和实际生效状态。

### Modified Capabilities

- `agent-chat-ui`: 模型选择菜单需要根据当前模型能力展示思考开关、深度选项、模型默认值和不支持说明，并明确模型思考与界面可审计过程相互独立。
- `runtime-reasoning-policy-enforcement`: 运行时需要区分模型级思考配置与 Agent 推理策略，绑定不可变的实际模型思考配置并兼容旧请求。
- `reasoning-policy`: 明确 Agent 推理强度负责运行编排资源，显式模型思考配置负责 Provider 模型调用强度，避免两个控制项含义重叠。

## Impact

- 前端主要影响聊天框 `ModelMenu`、模型选项数据结构、按模型隔离的本地偏好、运行请求类型、过程说明与中英文文案。
- 后端主要影响 Run 请求 schema、模型能力/推理适配器、ModelClient 绑定、运行快照与 usage metadata。
- API 将新增模型思考能力读取接口或等价的模型目录字段，并在 `model` 运行配置中接受可选的思考设置；现有字段保持兼容。
- 预计不新增第三方依赖；若持久化到 Run 独立字段则需要数据库迁移，否则复用现有 JSON 快照字段。
