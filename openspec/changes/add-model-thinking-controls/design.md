## Context

当前聊天框的模型菜单已经同时承载模型选择与可信对话策略，`reasoning_effort=fast|balanced|deep` 会控制 Agent 轮次、工具、反思等编排预算，并由 `model_reasoning.py` 顺带映射为部分 Provider 的模型推理参数。这个复用造成两个问题：标准模式没有模型思考控制；不同模型支持的开关、档位和预算不一致，却被统一显示成三个 Agent 档位。

聊天消息里的“思考中 / 思考完成”和展开后的“思考”条目来自 Astra 的 `reasoning.phase.*`、`reasoning.summary.*`、AgentTurn、ToolCall 和验证事件。这里展示的是运行状态与模型显式返回的简洁 `reasoning_summary`，不是 Provider 的隐藏思维链，也不依赖 Provider 是否启用扩展思考。

模型配置目前由前端按 Provider/模型提交，Run 的 `model_policy` JSON 已保存 Provider 与模型信息，ModelInvocation 的 usage metadata 也已记录适配结果。设计应复用这些持久化点，不能保存隐藏思考正文，也不能让前端直接拼接任意 Provider 参数。

## Goals / Non-Goals

**Goals:**

- 用一个可查询的能力描述表达每个 Provider/模型的思考开关、深度集合、默认值和限制。
- 在聊天框模型菜单中提供与当前模型匹配的思考控制，并按模型恢复偏好。
- 在创建、继续和审批后继续运行时绑定同一份不可变的有效配置。
- 由后端完成校验、降级和 Provider 参数映射，并记录 requested/effective 结果。
- 保证模型思考开关和深度不控制界面可审计过程的产生、可见性或展开状态。
- 明确用户选择的同一模型思考深度在快速模式和可信模式中的性能、质量与执行保证影响，同时保持选择独立于回答模式。
- 保留未携带新字段的旧客户端行为。

**Non-Goals:**

- 不向用户展示、持久化或转发模型隐藏 chain-of-thought。
- 不允许用户直接输入 `thinking_budget`、`reasoning_effort` 等任意 Provider 原生字段。
- 不在本变更中实现新的 Gemini 原生 Transport 或扩展新的模型供应商。
- 不改变 Agent 的安全门、工具审批、反思开关或完成验证。
- 不把界面“思考过程”改造成供应商隐藏推理内容查看器，也不新增关闭过程审计的联动开关。

## Decisions

### 1. 能力解析由后端提供单一事实来源

新增纯函数能力解析器，输入 `provider + model`，输出稳定的 `ModelThinkingCapability`：

- `supported`
- `toggle`：`optional | always_on | unavailable`
- `depths`：有序的规范化深度项，每项含稳定 ID 和展示标签
- `default_enabled`、`default_depth`
- `reason`：不支持或受限原因
- `capability_version`

前端通过批量能力解析接口为已启用模型加载描述。选择后端解析而不是在前端复制型号规则，可避免 UI 与实际请求适配器漂移；能力解析器与请求参数解析器共享同一型号规则表。

### 2. 使用规范化选择，不暴露 Provider 原生参数

运行请求的 `model` 配置新增可选 `thinking` 对象：

```json
{
  "enabled": true,
  "depth": "high",
  "capability_version": 2
}
```

深度 ID 从模型能力响应中选择，可包含 `minimal`、`low`、`medium`、`high`、`xhigh`、`max` 的子集。Provider 适配器负责把 ID 转为 effort、开关或有界 token budget。这样既能表达模型差异，也防止任意字段透传到第三方 API。

### 3. 显式模型思考覆盖旧的隐式映射

运行时先解析显式 `model.thinking`。存在时，它只控制单次模型调用的思考参数；`reasoning_policy.reasoning_effort` 只继续控制 Agent 编排资源。不存在时，为兼容旧客户端，继续按现有 `reasoning_effort` 映射模型参数，并把来源标记为 `legacy_reasoning_policy`。

这一优先级能渐进发布而不破坏旧请求，同时消除新 UI 中“任务策略”和“模型思考深度”相互覆盖的问题。

### 4. 无效或过期选择采用可观测的安全规范化

后端不信任前端能力缓存。创建或继续运行时重新解析能力：

- 不支持思考的模型忽略思考字段并返回 `unavailable`。
- `always_on` 模型拒绝关闭意图，规范化为开启并记录原因。
- 已移除的深度回退到该模型默认深度。
- 缺失开关或深度使用能力默认值。

规范化结果写入 Run 的 `model_policy.thinking`，包含 `requested`、`effective`、`source`、`adapter` 和调整原因；每次 ModelInvocation usage 继续记录最终发出的非敏感参数摘要。复用 JSON 字段，无需数据库迁移。

### 5. 偏好按模型键保存在前端，Run 快照是执行依据

前端使用版本化本地存储，以 `provider:model` 为键保存用户选择的 `{enabled, depth}`。模型切换时先与最新能力求交集：有效则恢复，无效则采用模型能力声明的中性默认值并更新缓存。回答模式不参与偏好键，也不在模式切换时自动升降思考深度；同一模型在快速和可信模式中使用同一份用户选择，直到用户主动修改。此偏好仅用于下一次运行；运行开始后，后续 UI 修改不得改变当前 Run 的有效快照。

创建 Run、等待用户后继续以及批准后继续都提交当前模型选择。已有 Run 的恢复流程优先使用 Run 快照，防止中途切换模型导致思考配置漂移。

### 6. 控件与 Agent 策略分区显示

“思考”开关和“思考深度”紧邻当前模型，标准与可信模式均可见；“推理资源、工具上限、反思”等仍留在可信策略区。无思考能力时显示简短说明而不是无效控件；强制思考模型显示锁定开启状态。模型按钮摘要显示当前有效选择，移动端保持可点击尺寸和键盘可访问性。

控件名称使用“模型思考”和“模型思考深度”，并在过程面板附近提供简短说明：“此处展示 Astra 的公开执行过程摘要，不是模型隐藏思维链。”改变模型思考设置不得隐藏、清空、展开或折叠过程面板，也不得改变 `reasoning.summary.*` 事件协议。

### 7. 回答模式不分配模型思考预算，只改变同一选择的影响范围

模型思考开关与深度是模型菜单中的独立用户选择。快速模式和可信模式 MUST NOT 为它分配不同预算、裁剪可选深度、自动升降选择或在模式切换时覆盖偏好。用户未选择过时只使用模型能力声明的中性默认值，不使用回答模式推导默认值。

模型思考深度在两种回答模式中都表示单次模型调用可使用的内部推理资源，不改变 AnswerMode。区别只来自两种模式本身调用路径不同：

| 维度 | 快速模式（standard） | 可信模式（trusted） |
| --- | --- | --- |
| 用户选择 | 使用当前模型的同一份显式选择 | 使用当前模型的同一份显式选择 |
| 主要收益 | 提高直接回答或工具决策对复杂问题的处理能力 | 提高计划、决策、反思与综合等多次调用的质量 |
| 主要代价 | 高深度会增加首字延迟、总延迟和 reasoning tokens，可能削弱“快速”体验 | 相同深度会随多次模型调用累积成本和延迟，影响通常更大 |
| 不会改变 | 不新增完整计划、严格验证或反思循环 | 关闭或降低模型思考不会关闭计划、审批、安全门和严格验证 |
| 界面过程 | 始终由运行事件和公开摘要决定 | 始终由运行事件和公开摘要决定 |

UI 对快速模式中的高深度显示“可能显著降低响应速度”，对可信模式中的高深度显示“将应用于本次运行的多次模型调用，可能增加耗时与用量”。这些是影响说明，不是预算或限制；运行时不得因模式静默抬高或降低用户选择。

可信模式的选定深度统一应用于该 Run 中支持思考参数的模型操作，以保持可预测性。由于可信模式包含更多模型调用，第一版不做隐式的按 operation 自动降档；未来若引入自适应分配，应作为独立能力并在 Run 快照中暴露每个 operation 的有效深度。

## Risks / Trade-offs

- [型号规则会随供应商更新而过期] → 使用显式 allowlist、能力版本和安全默认值，并为未知型号返回 unavailable。
- [“Agent 推理强度”与“模型思考深度”仍可能让用户困惑] → 分区、改进文案，并在策略说明中解释两者分别控制编排和单次模型调用。
- [界面“思考”被误认为模型隐藏思维链或思考开关的结果] → 将其定义为 Astra 可审计过程摘要，使用明确说明并测试模型思考关闭时过程事件仍正常展示。
- [可信模式高深度的成本被多次模型调用放大] → 提供模式影响提示和可审计 usage；第一版保持用户选择的统一深度，不做不可见的 operation 降档。
- [本地偏好无法跨浏览器同步] → 本阶段保持与当前模型选择相同的本地策略；Run 快照保证审计与重放。服务端同步可后续单独增加。
- [能力查询增加一次加载请求] → 使用批量接口、内存缓存和纯函数解析；失败时隐藏可变控件并使用兼容默认行为。
- [旧客户端与新客户端产生不同来源] → 在 Run 快照和 usage metadata 中记录 `explicit_model_control` 或 `legacy_reasoning_policy`。

## Migration Plan

1. 上线共享能力矩阵、请求 schema、规范化与适配测试，保持旧请求路径。
2. 上线能力查询接口和 Run 快照/usage 记录。
3. 上线前端模型菜单控制、按模型偏好和兼容文案。
4. 用可选开关模型、强制思考模型、不支持模型及旧请求各完成一次端到端验证，并分别覆盖快速和可信模式。
5. 验证思考关闭、低深度与高深度均不会改变过程面板事件、可见性和审计摘要安全边界。

回滚前端后，后端继续接受旧请求；回滚后端前应先回滚前端的新字段发送。由于复用 JSON 字段，不需要数据库降级。

## Open Questions

- 是否在具备准确价格信息后，为深度选项补充预估延迟与费用提示。
