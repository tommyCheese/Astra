## Why

Astra 后端已经形成完整但高度集中的执行系统：核心流程、持久化、领域模型和 API 投影持续堆叠在少数超大文件与超长方法中，阅读者必须同时理解过多概念才能安全修改代码。当前最突出的问题不是格式，而是命名、职责、依赖方向和源码边界未能忠实表达领域；现在需要以可读性为第一优先级开展一次允许大规模改动的系统性重构，并在保持外部行为与安全语义的前提下建立可持续的架构约束。

## What Changes

- 按业务能力和执行阶段重新划分后端模块，使每个模块只表达一个清晰、可命名的概念；拆分 `agent_loop.py`、`repositories/runs.py`、`db/models.py`、`schemas/agent.py`、`model_client.py`、`tools/web.py`、skills 与 memory 等高复杂度热点。
- 将 Agent 主循环改造为显式阶段编排：上下文准备、决策、权限判定、工具调用、观察、评估、反思、完成验证与终态收敛分别由窄接口组件负责，主编排器只呈现业务流程。
- 按聚合与用例拆分 Repository、ORM 模型和 API read projection，明确事务边界，消除持久化层对 runner 实现细节的反向依赖。
- 建立单向依赖规则和组合根：传输层调用应用用例，应用层编排领域服务与端口，基础设施层实现端口；调度器不再导入 API 私有函数，跨领域协作通过显式服务接口或事件完成。
- 统一领域词汇和命名，移除含义不清的缩写、泛化变量名与同义概念；公共类型、方法和模块名称必须表达业务意图，注释解释原因与约束而非复述代码。
- 用类型化值对象、枚举、结果类型和专用 DTO 缩小 `dict[str, Any]`、魔法字符串、宽泛参数与隐式状态转换的使用范围；清除无依据的 `type: ignore`。
- 将应用装配、生命周期、HTTP middleware、异常映射和路由注册从 `main.py` 拆分，统一依赖注入与测试替身边界。
- 引入自动化架构与可维护性护栏，包括依赖方向检查、循环依赖检查、复杂度/文件规模预算、公共 API 类型检查、命名与 lint 规则，并记录有时限的例外。
- 采用 characterization tests、契约测试和分阶段迁移保持 HTTP/SSE、数据库、权限、安全、恢复、调度与 Artifact 行为兼容；每个迁移切片在删除旧路径前完成等价验证。
- 更新后端架构文档、模块地图、领域术语表与贡献指南，使文档中的概念、依赖方向和真实代码保持一致。
- **BREAKING（仅后端内部）**：内部 Python 模块路径、类名、函数名和构造方式将发生较大调整；不承诺兼容未公开的 `app.*` 导入路径。公开 HTTP/SSE 契约、持久化数据和产品行为原则上不变，任何必要的外部变更必须另立提案。

## Capabilities

### New Capabilities

- `backend-maintainable-architecture`: 定义后端可读性、模块职责、依赖方向、命名、类型边界、复杂度护栏、行为兼容与架构文档的可验证要求。

### Modified Capabilities

无。本变更重构实现结构，不改变现有产品能力的需求语义。

## Impact

- 后端代码：`backend/app` 下的 API、runner、subagents、repositories、db、schemas、permissions、tools、skills、memory、scheduling、workspace/sandbox 及应用装配代码。
- 测试：现有后端测试需要按公共行为与模块边界重组，并增加 characterization、架构依赖、事务边界和阶段编排测试。
- 数据与接口：默认不新增数据库迁移，不改变公开 HTTP/SSE 契约；若拆分 ORM metadata，仍必须保持表名、列、关系、迁移历史与历史数据兼容。
- 工程流程：CI 增加架构和复杂度检查；后续后端改动需要遵循新的模块地图、术语表与依赖规则。
- 协作风险：这是跨模块的大型重构，将通过可独立验证的迁移切片、兼容门面和短生命周期适配层控制合并风险；不以减少 diff 规模为目标，以最终代码清晰度为目标。
